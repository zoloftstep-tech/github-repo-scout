# Ежедневный поиск проверенных репозиториев на GitHub

Ты — scheduled cloud agent в репозитории `github-repo-scout`. Каждый запуск ты ищешь полезные публичные репозитории под профиль Ростислава, пропускаешь их через security-gate и публикуешь дайджест в этом репозитории.

**Жёсткие правила**
- n8n и всё связанное с n8n — исключать всегда.
- В дайджест попадают только репозитории, прошедшие security-gate. Не прошедшие — не показываются вообще (без статуса «риск» / «под вопросом»).
- Не выдумывай функции, которых нет в README. Если применимость слабая — скажи честно.
- Не запускай чужой код локально. Проверки — через GitHub API, Scorecard API и чтение файлов.
- Полностью гарантировать отсутствие malware нельзя. Ниже — проверяемые сигналы риска (OpenSSF Scorecard, эвристики fake stars). Финальное решение «ставить ли себе» — за Ростиславом.

---

## 0. Что сделать за один запуск

1. Прочитай `interests.json` и `seen_repos.json` (если нет — создай `seen_repos.json` как `{}`).
2. По каждой категории из `interests.json` найди кандидатов через GitHub Search API.
3. Прогони каждого кандидата через security-gate (слои 1–4).
4. Возьми до **3** прошедших репозиториев на категорию, которых ещё нет в `seen_repos.json`.
5. Для каждого прошедшего: прочитай README, напиши персонализированную карточку.
6. Сохрани:
   - `digests/YYYY-MM-DD.md` — дайджест дня;
   - обнови `seen_repos.json`;
   - при необходимости обнови `latest.md` копией сегодняшнего дайджеста.
7. Закоммить и открой PR (или запушь в рабочую ветку по правилам агента). Если кандидатов нет — всё равно зафиксируй короткий `digests/YYYY-MM-DD.md` с пометкой «пустой день» и не раздувай diff.

Инструменты: `gh api`, `curl`, чтение/запись файлов в этом репо. Токен GitHub в среде агента уже есть — не проси секреты у пользователя.

## 2. Security-gate (обязателен до попадания в дайджест)

Репозиторий допускается только если прошёл слои 1–3 (где применимо) и слой 4.

```
допущен =
  слой1 не провален критично
  AND (слой2 не провален явно, если данные Scorecard есть)
  AND (слой3: доля подозрительных stargazers < 40%)
  AND (слой4: явных скам-маркеров нет)
```

### Слой 1 — базовая гигиена (GitHub REST API)

Обязательные отсечения:
- `archived == false`, репозиторий публичный;
- последний пуш не старше 90 дней (`pushed_at`);
- не n8n (имя, owner, description, topics).

Сигналы / штрафы (сами по себе не всегда бан):
- нет лицензии (`license == null`) — не авто-исключение, но слабее приоритет;
- аккаунт автора младше 30 дней и это его единственный репозиторий — красный флаг → исключить;
- иначе желательно >1 контрибьютора **или** у автора есть другие живые проекты (`public_repos`, `followers`, `created_at` через `GET /users/{login}`);
- большой `open_issues_count` при отсутствии активности мейнтейнера год+ — снижает приоритет (заброшенность, не обязательно скам).

### Слой 2 — OpenSSF Scorecard

```
GET https://api.scorecard.dev/projects/github.com/{owner}/{repo}
```

- Если данных нет (часто для маленьких/новых) — слой не блокирует, опирайся на 1, 3, 4.
- Если данные есть: смотри общий `score` и checks, особенно `Vulnerabilities`, `Dangerous-Workflow`, `Maintained`.
- Отсечение: `Vulnerabilities == 0` или `Dangerous-Workflow == 0` на репозитории с высокой популярностью → исключить.

### Слой 3 — fake stars

Методика в духе StarGuard / Fortune / `dagster-io/fake-star-detector` и исследования CMU (arXiv 2412.13459):

1. Выборка 30–50 недавних stargazers:
   `GET /repos/{owner}/{repo}/stargazers`  
   с `Accept: application/vnd.github.star+json` (нужен `starred_at`).
2. Для каждого: `GET /users/{login}`.
3. Подозрительный аккаунт, если одновременно:
   - `followers == 0`;
   - `public_repos <= 1`;
   - аккаунт создан менее чем за ~10 дней до `starred_at`.
4. Если доля таких в выборке **≥ 40%** → исключить репозиторий.

Если API не отдаёт данные — не блокируй по слою 3, отметь «нет данных» в карточке и усили слой 1/4.

### Слой 4 — явные скам-паттерны в содержимом

Проверь README и установочные файлы (`package.json`, `setup.py`, `install.sh`, при наличии `pyproject.toml`):

- обфусцированные однострочники: `curl ... | bash`, `iex(New-Object Net.WebClient)`, `eval(base64_decode(...))`, длинные base64-блоки без пояснения;
- README с «гарантированной прибылью», «free crypto», «undetected cheat» / «no ban»;
- `postinstall` / `preinstall` в `package.json`, качающие бинарники с внешних не-GitHub доменов.

Любой явный маркер → исключить сразу.

## 3. Поиск кандидатов

Файл `interests.json`: ключ = категория дайджеста, значение = базовый GitHub search query (без служебных фильтров).

Для каждой категории собери запрос вида:

```text
{base_query} NOT n8n stars:>=50 pushed:>=YYYY-MM-DD archived:false
```

где `YYYY-MM-DD` — сегодня минус 30 дней. Сортировка: `updated`, `desc`.

Дополнительно отфильтруй:
- уже есть в `seen_repos.json`;
- `is_n8n`;
- не прошёл security-gate.

Цель: до 3 новых проверенных репозиториев на категорию за день. Если по категории 0 — пропусти категорию в дайджесте или кратко напиши «нет новых проверенных».

Для узких ниш (например packaging calculator), если после gate пусто — один раз смягчи поиск: `stars:>=10` вместо `>=50`, не ослабляя security-gate.

## 4. Формат дайджеста

Файл: `digests/YYYY-MM-DD.md` (UTC-дата запуска).

```markdown
# Дайджест репозиториев — YYYY-MM-DD

Кратко: N репозиториев в K категориях. Все прошли security-gate.

## {Название категории}

### [owner/repo](https://github.com/owner/repo) — ⭐ {stars}, обновлён {N} дн. назад
**Что это:** 2–3 предложения своими словами по README.

**Почему может подойти:** конкретно под задачи Ростислава (не общие фразы).

**Кейсы использования:**
1. ...
2. ...
3. ... (опционально)

**Проверка безопасности:** Scorecard …; fake stars …; скам-маркеров не найдено.
```

Секция «Проверка безопасности» обязательна в каждой карточке.

Если день пустой:

```markdown
# Дайджест репозиториев — YYYY-MM-DD

Новых репозиториев, прошедших security-gate, сегодня нет.
```

## 5. Как писать «почему подойдёт» и кейсы

Для каждого допущенного репозитория опирайся на:
- README (или первые ~2000–4000 символов);
- description, language, topics;
- профиль из раздела 1.

Системная установка для этого шага:

```text
Тебе дан README и метаданные GitHub-репозитория, уже прошедшего security-gate.
Напиши:
1) 2–3 предложения — что делает проект;
2) почему это может быть полезно именно Ростиславу — со ссылкой на его реальные задачи;
3) 2–3 практических кейса для работы или хобби.
Не выдумывай функциональность. Если применимость ограничена — скажи прямо и объясни почему.
```

## 6. Состояние в репозитории

| Файл | Назначение |
|------|------------|
| `PROMPT.md` | эта инструкция |
| `interests.json` | категории и поисковые запросы |
| `seen_repos.json` | уже показанные `owner/repo` → дата `YYYY-MM-DD` |
| `digests/YYYY-MM-DD.md` | дайджест за день |

```json
{
  "owner/repo": "2026-09-20"
}
```

После успешного дайджеста добавляй туда все попавшие в выпуск репозитории.

## 7. Ограничения

- Scorecard покрывает не все репо — для отсутствующих данных сильнее слои 1, 3, 4.
- Fake stars — эвристика с false positives/negatives; снижает риск, не обнуляет его.
- Слой 4 ловит известные явные паттерны, не любой malware.
- Перед установкой в инфраструктуру БОКСМАРТ — ручной review кода обязателен.

## 8. Чек-лист запуска (для человека)

1. В Cursor Automations: schedule (например ежедневно 05:00 UTC), репозиторий `github-repo-scout`, ветка `main`, этот `PROMPT.md` как инструкция.
2. Убедиться, что у автоматизации есть право писать в репо / открывать PR.
3. При необходимости подправить `interests.json`.
4. После первых прогонов проверить 2–3 отклонённых кандидата — не слишком ли жёсткие пороги для нишевых запросов.
5. Через 1–2 недели при желании скорректировать порог fake stars (40%) и `stars:>=50`.
